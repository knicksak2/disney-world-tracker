## Findings

### HIGH

**H1. The recap read never re-checks that the recipient is still a Friend of the sharer, so an unfriended person keeps live access to every crew member's photos.**
Where: requirements.md R15.3, R15.6, R15.11, R15.12 (labels the route "friend-gated"), D22 consequences text; design.md "Summary share", Property 21; tasks.md 21.2, 21.3.
Problem: R15.3 lists the conditions for photos: recipient row present and not deleted, `includePhotos`, sharer still a member, Trip exists, photo approved, no block. A current Friendship is not among them. The code confirms the gap is real: `friends/repo.ts removeFriend` only runs `DELETE FROM friendships ...` and does not touch `shares` or `share_recipients`, and `sharing/repo.ts openShare` does not look at friendships either. The existing `InboxScreen` guards this only on the client (it checks `stillFriend` before navigating and shows `SENDER_TAP_UNAVAILABLE_COPY`), which a direct API call bypasses. D22 lists the only ways access ends (recipient deletes, sender leaves, Trip deleted) and omits unfriending, while there is also no sender revoke. A sender who unfriends someone because of a falling-out cannot cut off that person's access to photos of the whole crew, and every call mints fresh presigned URLs. The visibility matrix in design.md says "a Friend of the sharer", which the implementation would not enforce.
Fix: Add a condition to R15.3 and R15.12: "the recipient is currently a Friend of the sharer (one `friendships` primary-key lookup via `canonicalPair`, the same table `createShareAtomic` reads)". When it fails, answer the collapsed `validation_failed` (the same response as a deleted share). Add "recipient is or is not currently a Friend" as a dimension to Property 21's generator and to the task 21.3 matrix, with a test that unfriends after the share is sent and asserts the next `GET /me/inbox/:shareId/trip-recap` is `validation_failed` with no figures and no URL. Add unfriending to the D22 consequences list and to R15.11's residual-window wording. In task 22.4, reuse the existing `stillFriend` pre-check in `InboxScreen` for the tripSummary card.

### MEDIUM

**M1. `TripRecapDTO.superlatives` is typed as `string[]`, but the real data is `TripSuperlativeDTO[]` with `memberId` and `memberDisplayName`; "no per-member names" is contradictory and the planned test conflicts with it.**
Where: design.md `TripRecapDTO` (`superlatives: readonly string[]`); requirements.md R15.12; tasks.md 17.1 and 21.3; `packages/shared/src/trips.ts` (`TripSuperlativeDTO` has `id, title, description, icon, memberId?, memberDisplayName?, experienceName?, value?`); `TripSummaryScreen.tsx formatSummaryShareText` prints `sup.memberDisplayName` ("Group MVP: <name>").
Problem: R15.12 says the recipient sees "superlatives" and also "no per-member names or ratings". Superlatives are per-member by construction (`summary.ts` sets `memberId` on Group MVP, Lead Explorer, Best Co-Pilot, Chief Critic). A `string[]` does not exist upstream, so the implementer must invent a projection. Task 21.3 asserts that "perMember data ... profiles" sentinel strings are absent from the response; if the implementer passes `memberDisplayName` through (as the text share does), that sentinel test fails, and if they pass `memberId` through, crew user ids reach non-members.
Fix: Define the projection in the design: `superlatives: ReadonlyArray<{ id: string; title: string; description: string; icon: string; experienceName?: string; value?: string | number; memberDisplayName?: string }>`, never `memberId`. Decide explicitly whether `memberDisplayName` is allowed (the OS text share already exposes it, so "no more than the text share" permits it) and reword R15.12 to "no member ids and no per-member contribution counts or ratings". Make the 21.3 sentinel test match the decision: assert `memberId`/`actor_id`/user ids and `perMember` keys are absent, and the display-name sentinel appears only through the allowed field.

**M2. What the recap route returns for the figures when the sharer has left the Trip or the Trip is deleted is undefined, and as written it keeps serving live figures to a former member's Friends.**
Where: design.md Error Handling rows "Recap read (recipient) ... Sharer left the Trip, or Trip deleted -> 200 with photos access unavailable"; R15.6; R15.12; `TripRecapDTO` (numbers are non-optional).
Problem: Only the `photos` part is said to be `unavailable`. For a deleted Trip, `repo.getSummary(tripId)` has nothing to read, so the response either errors or returns zeros that look like a real empty trip. For a sharer who left or was removed, the route still computes and returns `distinctExperienceCount`, planned counts, superlatives and top rated for a Trip the sharer can no longer see, to anyone they shared with, indefinitely. R15.6 only promises that the photos part goes `unavailable`.
Fix: Pick one and write it into R15.12 and Property 21: when the Trip is gone or the sharer is no longer a member, answer `200` with `recap: null` and `photos.access: 'unavailable'` (the card then shows "This recap is no longer available"), or the collapsed `validation_failed`. Make the figure fields optional in `TripRecapDTO` or wrap them in a nullable `recap` object. Add a test for each case asserting no figure and no URL appears.

**M3. The kill switch removes the recap route (so figures vanish too), and a disabled plugin leaves `member_post` items leaking raw `metadata.photoIds`.**
Where: design.md routes section ("When `PHOTOS_ENABLED=false` the plugin registers only `GET /photos/config`"); R20.2; design.md file tree (`summaryShareRoutes.ts` inside the photos service); R14.10; trips `routes.ts` feed handler (today `return repo.getFeed(id, userId)`).
Problem: `GET /me/inbox/:shareId/trip-recap` lives in the photos plugin, so with `PHOTOS_ENABLED=false` (the default, and the emergency switch) it answers 404 and a recipient cannot open the recap at all, even though the recap's figures have nothing to do with photos. The tripSummary share itself is created in the Sharing service and still works, so the user can send a card that cannot be opened. Separately, the trips feed route strips `photoIds` only when it calls the optional `FeedPhotoPort`. With the port absent, any `member_post` created earlier is returned with `metadata.photoIds` and no slots.
Fix: Register the recap route from the Sharing/trips side (or register it always) and return `photos.access: 'unavailable'` when photos are disabled. State in R20.2 that this route is the one exception. For the feed, require the trips route to drop `photoIds` and the item itself (or return it with an empty `photos` array) when the port is absent. Add tests for `PHOTOS_ENABLED=false`: recap opens with figures and `unavailable`; feed read returns no `photoIds`.

**M4. The cross-service dependencies of share creation and the recap read are not defined: `sharingRoutes` has no pool or trips port, and nothing says which module owns `getSummary`.**
Where: design.md "Summary share" ("`POST /me/shares` composes the payload server-side after `assertTripMember` + `can(role,'share_trip_summary')`"); tasks.md 21.1, 21.3; `apps/api/src/services/sharing/routes.ts` `SharingRoutesOptions`; `trips/authz.ts assertTripMember(pool, userId, tripId)`; `trips/repo.ts getSummary(tripId)`.
Problem: `SharingRoutesOptions` has `repo`, `requireSession`, `emitShareDelivered`, `computeProgressShareStats`, `resolveSenderDisplayName` and nothing else. `assertTripMember` needs a `DbPool`, `can` needs the role, the payload needs `tripName`, and the recap needs `deriveTripSummary` inputs (four live reads in `getSummary`). The spec cites `deriveTripSummary`, which takes a prepared `TripSummaryInput`, not a trip id. The design names no port, no `composeServices.ts` wiring change, and no owner for the route. An implementer will import the pool or the trips repo directly into Sharing, which the repo's conventions (constructor injection through structural ports) forbid.
Fix: Add to the design a `TripShareFacts` port, for example `{ roleOf(userId, tripId): Promise<TripRole | null>; tripName(tripId): Promise<string | null>; isMember(userId, tripId): Promise<boolean>; summary(tripId): Promise<TripSummaryDTO | null> }`, implemented in `composeServices.ts` from `tripRepo` and the pool, passed to the Sharing plugin (optional, like `computeProgressShareStats`) and to the recap route. Say that the recap route calls `tripRepo.getSummary` and projects it. Name the wiring task (21.1 or 21.3) and add a wiring test in the style of the existing "production registration" tests.

**M5. The highlight rule groups by upload day (`created_at`), so a normal "upload everything at the end" pattern yields one or two highlights, although the Album already has a validated capture time (`sort_at`).**
Where: requirements.md D21, R26.6; design.md "`selectRecapHighlights`"; tasks.md 5.5; `photos.sort_at` / `taken_at` in migration 0062; R13.3.
Problem: `created_at` is the time of the initiate call. A family that picks 25 photos from the camera roll on the last night produces photos from several trip days that all share one New York upload day, and the rule returns exactly one photo. The spec flags "upload day" as an assumption the owner did not spell out, but it was not weighed against a field that already exists: `sort_at` is the client-declared capture time when it falls between 2000-01-01 and request time plus 5 minutes, and the request time otherwise (R13.3), so it degrades to today's behavior when the metadata is missing. It is the same field the Album sorts and groups by (R13.6 groups the Album by New York day), so the recap and the Album would disagree about which day a photo belongs to.
Fix: Group by `sort_at` instead of `created_at`: rename the pure function's input field to `sortAt`, change `selectRecapHighlights`, Property 38, tasks 5.5, 19.4, 21.3, R13.7, R15.5 and R26.6 together, and keep the tie-break `(sortAt, id)`. If the owner prefers upload day, record that choice with the bulk-upload consequence in D21 so it is a conscious veto and not an oversight.

**M6. Post creation validates the photos and then updates them with no row lock and no guarded update, so a photo can land in two posts or change state between check and link.**
Where: design.md "Trip posts (Phase 2)" (`UPDATE photos SET feed_item_id=$1 WHERE id = ANY($2) AND owner_id=$3`); R14.2; tasks.md 20.1.
Problem: The transaction validates `feed_item_id IS NULL` and the status set with a plain SELECT, then runs an UPDATE whose WHERE clause has neither `feed_item_id IS NULL` nor the status condition, and checks no row count. Two concurrent `POST /trips/:id/feed/posts` calls (a double tap or a retry after a timeout) with the same photo id both pass validation under READ COMMITTED; the second UPDATE overwrites the first link. Both posts list the photo in `metadata.photoIds`; deleting post A then marks the photo `deleted`, which blanks it in post B. A photo whose status moved to `rejected` or `deleted` between the SELECT and the UPDATE is linked anyway. Property 22 and the 20.1 tests cover only serial calls.
Fix: In the validation SELECT use `... FOR UPDATE`, or make the UPDATE conditional (`WHERE id = ANY($2) AND owner_id = $3 AND feed_item_id IS NULL AND status IN ('pending','approved','needs_review') RETURNING id`) and roll back with `validation_failed` when the returned count differs from the requested count. Add a test that fires two creates with the same photo and asserts exactly one succeeds and the other creates no feed row (in pg-mem, run the second create after the first and assert `feed_item_id IS NULL` is enforced; say that true concurrency is not provable there, as the design already does for the advisory lock).

**M7. `DELETE /trips/:id/feed/posts/:feedItemId` is not specified to verify that the feed item belongs to `:id` and is a `member_post`.**
Where: design.md routes table and "Trip posts"; tasks.md 20.1; contrast `trips/repo.ts assertTargetInTrip`, which does check `trip_id` for reactions and comments.
Problem: The route is gated by `assertTripMember` and `author or delete_any_trip_photo` for `:id`, but the spec never says the feed item row must satisfy `trip_id = :id AND type = 'member_post'`. As written, an organizer of Trip A could pass the id of a post in Trip B, and the handler would soft-delete the photos listed in its `metadata.photoIds` and delete its reactions and comments. A member could also delete their own system feed items (`completion_logged` and so on) through this route. The 20.1 tests list "a non-author non-organizer cannot delete" and nothing about a foreign trip or a wrong type.
Fix: State in the design and R14.7 that the post is loaded with `WHERE id = $1 AND trip_id = $2 AND type = 'member_post'` and anything else answers `trip_not_found` (the code the existing target check uses). Add tests in 20.1: a post id from another trip (even when the caller is an organizer there) is refused and its photos stay untouched; a non-`member_post` feed item id is refused.

**M8. Whether a member who left or was removed can still delete their own Trip photos is contradicted three ways.**
Where: requirements.md R12.5 ("at any time"), R12.6 (a former member requesting a Trip Photo gets `trip_forbidden` and the photos stay in the Album), D19 rationale ("a departed member (D10) can no longer remove their own photos"), D23 ("an uploader's only control is deleting their own photo (anytime)"), R12.7; design.md routes row `DELETE /photos/:id` ("uploader, or `canDeleteOthers`").
Problem: D19 says a departed member cannot delete; R12.5, D23 and the routes table say the uploader always can; R12.6 is ambiguous about whether "requests" includes delete. The outcome matters for privacy: R12.7 and D23 make deletion the uploader's only control over a photo that stays in the Album and in recap shares after they leave. If a departed member cannot delete, they have no control left at all.
Fix: Decide and write it once. Recommended: the uploader may delete their own Trip photo regardless of current membership (the route authorizes on `owner_id`, never on membership), R12.6 is limited to reads and uploads, and D19's rationale sentence is reworded. Add a test in 19.2 or 19.1: a removed member's `DELETE /photos/:id` on their own photo succeeds, the same call on a stranger's photo is `photo_not_found`, and a removed member's `GET /trips/:id/photos` is `trip_forbidden`.

**M9. With `PHOTOS_REPORT_AUTOHIDE_TRIP` at 1 and R16.8, any Friend who received a recap can hide a crew member's photo from the whole Trip with one report.**
Where: requirements.md R16.4 (threshold 1 for trip photos), R16.8 (reports accepted from share recipients), R16.5, R16.6; design.md Config row `PHOTOS_REPORT_AUTOHIDE_TRIP = 1`.
Problem: A recipient is not on the Trip, may not know anyone on it, and still has a one-report veto over photos the crew uploaded. A hidden photo disappears from the Album and recap for everyone but its owner until an operator restores it (R16.6). With the pointer design the sharer's Friends can be numerous and the cost is one request per photo, within the per-user rate limit. This is a griefing path created by combining two individually reasonable rules.
Fix: Count a report toward auto-hide for a Trip photo only when the reporter is a current Trip member; a report that arrives through `shareId` still records a `Photo_Report` and shows in the admin queue but does not by itself reach the hide threshold (or counts with a separate, higher threshold). Add the rule to R16.4/R16.8, to Property 13, and a test: a recipient's report of an approved Trip photo leaves it `approved` and queues it for review; a member's report hides it.

**M10. R16.8 and the design/tasks define "visible through a share" differently.**
Where: requirements.md R16.8 ("visible exactly when every condition of Requirement 15.3 holds for that share"); design.md "Summary share" ("the photo must be one of the share's current highlights, else `photo_not_found`"); tasks.md 21.3 (tests assert the stricter rule).
Problem: R15.3 conditions are about the share and the photo status/block, so under R16.8 any approved Trip photo is reportable and blockable with a valid `shareId`. The design and the 21.3 tests require the photo to be a current highlight, so a non-highlight approved photo answers `photo_not_found`. An implementer following the requirement fails the planned test, and one following the test violates the requirement. The stricter rule is the safer one (it prevents enumerating photo ids through a share).
Fix: Amend R16.8 (additive wording) to add "and the Photo is one of the share's current recap highlights (Requirement 15.5)", and cite 15.5 in the `_Requirements:_` line of 21.3.

**M11. Tasks 22.4, 22.5 and 22.6 sit in the same wave although each depends on another, and nobody clearly owns the shared photos section component.**
Where: tasks.md dependency graph wave 31 (`22.3`, `22.4`, `22.5`, `22.6`); task 22.4 ("renders the same photos section component as Requirement 26"); task 22.6 ("section component shared with the recipient's `TripRecapScreen` of task 22.4"); task 22.5 ("the new action navigates to the composer", which 22.4 creates).
Problem: 22.4 consumes a component that 22.6 builds, 22.6 says it is shared with 22.4, and 22.5 needs 22.4's composer route. An executor working in dependency order has no defined first step, and two tasks may each create the component.
Fix: Name 22.6 as the owner of the `TripPhotosSection` component and move it to wave 30 (it needs only 19.4, which is in wave 28). Move 22.4 and 22.5 to wave 31 and 32 respectively (or merge 22.5 into 22.4). Make 22.4 say "reuse `TripPhotosSection` from 22.6" and give the section a prop for the recipient mode (no Album action, `shareId` passed to report/block).

**M12. Task 17.1 does not add the Zod payload schema, and several share-kind consumers that `tsc` will not flag are unnamed.**
Where: tasks.md 17.1, 21.1, 22.4, Notes ("Exhaustive switches"); `packages/shared/src/schemas/Share.ts` (`sharePayloadSchema`, `pinShowcaseSharePayloadSchema`), `schemas/Inbox.ts` (`inboxItemSchema.payload: sharePayloadSchema`); `packages/shared/src/attention.ts` (lines ~530 and ~635 `if/else` on `pinShowcase`); `InboxScreen.tsx` (~543 navigation block, falls through to `FriendProfile` for any non-pinShowcase kind; ~1298 reaction values); `SentSharesScreen.tsx`; `shareBody.ts`; `NotificationCenterScreen.tsx`; `notifications/service.ts` (separate `ShareDeliveredEvent` union).
Problem: 17.1 adds a `SharePayload` TypeScript type and a `tripSummaryShareInputSchema` but not a `tripSummarySharePayloadSchema` in the `sharePayloadSchema` union, so `inboxItemSchema` and `inboxResponseSchema` (the repo's wire contract single source of truth) reject a tripSummary item. The Notes tell the executor to fix what typecheck reports, but the `if (payload.kind === ...)` chains in `InboxScreen` navigation and in `attention.ts` compile cleanly with a new kind: a tripSummary tap in `InboxScreen` would fall through to `navigation.navigate('FriendProfile', ...)` and the attention item gets no destination.

Add to 21.1/22.4 an explicit checklist of the consumers above (attention destination for tripSummary, `InboxScreen` navigation branch placed before the `FriendProfile` fallback, `SentSharesScreen` content branch, `shareBody.ts`, notification label in both unions) with a test for each that has behavior (attention destination, inbox navigation target).

## Specific checks requested

- Can a non-member, blocked user, removed member or non-Friend obtain a Trip photo URL or a recap?
