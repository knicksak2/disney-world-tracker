## 0. What this change is

A Friend who opens a shared Trip Recap gets a read-only, paginated album of ALL approved Trip photos (today the recap shows at most 6 highlights, one per New York day), behind the same share and the same gates. This widens the privacy boundary, so: spec first (D35, with a veto consequence), no new identity in any payload, serving keys only, `Cache-Control: private, no-store`, and the Friend re-check on every call.

Order: FEAT-001 spec amendments, FEAT-002 shared + API, FEAT-003 mobile. FEAT-003 needs FEAT-002's DTO/path. Do them strictly in that order.

## 2. Decisions made here (with reasons)

- **A1. Extract the gate once.** New `apps/api/src/services/sharing/tripRecapAccess.ts` exports `resolveShareAccess(gate, shareId, userId)` (throws the collapsed `AppError('validation_failed', 'Share not found in your inbox.')` on null) and `photoAccessFor(access, port)` (`!tripAvailable` -> `'unavailable'`; else `!includePhotos` -> `'not_included'`; else no port -> `'unavailable'`; else `'granted'`). The recap route is refactored to call them with identical behavior (its existing tests stay unchanged and are the regression). The new route calls the same two functions, so the gate cannot drift. The gate class itself is unchanged.
- **A2. New SQL lives in `DefaultRecapPhotoPort`** (pool-based, like `highlights`) rather than as new `PhotosRepo` methods. The Album SQL cannot be reused (it includes the viewer's non-approved photos and uploader columns). Adding a repo method would force `DefaultRecapPhotoPort` to take a repo for no gain. The block filter is copied from `SQL_TRIP_APPROVED_HIGHLIGHTS`; keyset predicate is the same OR form the Album uses (pg-mem friendly); cursor helpers are `encodeAlbumCursor`/`decodeAlbumCursor`. Selected columns are explicit: `p.id, p.sort_at, p.width, p.height` and nothing else (no `owner_id`, no keys), so identity cannot leak by accident.
- **A3. The port owns cursor decoding.** The route passes the opaque cursor string; `albumPage` throws `AppError('validation_failed')` for a malformed one. Sharing therefore never imports photo domain code (keeps D28 independence and the existing source guard).
- **A4. Widen D32 by a new port method `isAlbumPhoto`, keep `isHighlight`.** `service.ts` switches to `isAlbumPhoto`. `isHighlight` stays on the interface because its tests/fakes exist and it is the narrow predicate; it becomes unused by the service (no `noUnused*` error for a class method). Do not delete it in this change.
- **A5. Response `{ access, photos, nextCursor }`, new DTO `TripRecapPhotosDTO`** in `@dwt/shared`; items reuse `SharedSummaryPhotoDTO` and the server sets exactly its six non-optional keys (never `mine`).
- **A6. Mobile reuses `PhotoGrid`** with one additive optional item field `accessibilityLabel`, so each tile can have a distinct label ("Trip photo 3 of 12, opens viewer") without changing the dish-gallery default ("Guest photo").
- **A7. Mobile day grouping is extracted** to `apps/mobile/src/photos/dayGroups.ts` (generic over `{ sortAt: string }`); `TripAlbumScreen.tsx` re-exports `getNewYorkDayKey`, `formatNewYorkDayHeading`, and keeps `groupPhotosByNewYorkDay` as a thin wrapper, so `TripAlbumScreen.test.tsx` is the unchanged regression for the extraction.
- **A8. Block refetch comes from the existing invalidation.** `photoKeys.recapAlbum(shareId)` lives under `photoKeys.all`, which `useAddBlock` and `useReportPhoto` already invalidate. The screen adds `onBlocked` to also invalidate `tripRecapKeys.recap(shareId)` so the recap highlights drop the blocked uploader too. A test asserts the second album GET (this fails if the key were outside `photoKeys.all`).

Known limitations to tell the owner (not silently accepted):
1. Day-header counts count the photos loaded so far; while more pages remain the last loaded day can read lower than its final count. Exact counts would need a server field (a DTO widening), which is not in the approved scope.
2. If the recipient is also a Trip member, their own approved photos appear in the album; Report on one answers `photo_not_found` (the service refuses reporting your own photo) and the DTO has no `mine` flag. This already holds for highlights.
3. A current Trip member who reports through a `shareId` is still counted by `countedOpenReports` (it counts by membership, not by share). This is existing behavior under D31 and is unchanged.
4. Presigned URLs minted for a page stay valid for up to `PHOTOS_GET_URL_TTL_SECONDS` after a delete/unfriend (R15.11); this widens the number of URLs a Friend can hold from 6 to up to 100 per page.
