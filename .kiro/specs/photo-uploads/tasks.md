# Implementation Plan: Photo Uploads

## Overview

This plan adds one shared photo pipeline (client resize, presigned direct-to-R2 upload, confirm, asynchronous harm and food screening, reporting, blocking, admin review, and a cron-driven sweep) and two attach points. Phase 1 ships the pipeline and **food photos**. Phase 2 ships **trip photos** (Album, feed posts, the recap photos section with its pure highlight rule, and the in-app recap share to Friends). Phase 3 (other attach points) is future work and is described at the end only to name the extension points.

Read first, in order: `AGENTS.md`, every file in `.kiro/steering/`, `docs/hosting.md`, then this spec's `requirements.md` and `design.md`. The design's **Configuration & Constants**, **External Interfaces**, and **Correctness Properties** sections are authoritative: use the env var names, defaults, endpoint shapes, and formulas exactly. If something is ambiguous or missing a value, ask rather than guess.

**Dependencies and build order.** Depends on `trips`, `food-item-logging`, `friend-food-ratings` (rules only), `admin-panel` (extended by cross-reference), and the Sharing service. All of these exist at HEAD. Order: shared contracts, migration `0062`, config, pure domain, ports and adapters, repos, service, routes and wiring, admin queue, mobile Phase 1, docs. Then Phase 2: permissions, shared additions, migration `0063`, trip target, the `TripShareFacts` port and Sharing wiring (21.4), feed posts, summary share and recap route, report counting (21.5), mobile Phase 2. The Requirement 27 strip adds tasks 1.5, 3.3, 9.6, and 13.11 inside Phase 1 (see the Notes).

**Migration numbers.** `0061_trip_booking_timeline.sql` is the last file at HEAD. This plan uses `0062` (Phase 1) and `0063` (Phase 2). Re-check the directory before creating each file; never edit an applied migration.

**Secrets.** No key, token, or secret value may appear in code, specs, docs, fixtures, tests, logs, or commits. Only variable names. A Gemini key was pasted into a chat during planning; treat it as exposed and rotate it before first use (task 14.3).

**Code tasks versus launch gates.** Every numbered task except the four manual ones (12.2, 13.10, 14.3, 14.5) is code, tests, or docs that an executor can finish and check off. The manual tasks need the owner's accounts, keys, or physical devices and are **launch gates**: they sit in their own waves at the end of the dependency graph and no checkpoint depends on them. An executor must leave them unchecked and name them in the final report.

**Test discipline.** Tests ship in the same task as the code they cover (never deferred). Property tests use `fast-check` with at least 100 runs and the tag `// Feature: photo-uploads, Property N: <text>`. API tests use Vitest (`npx vitest run <path>`), mobile tests use Jest (`npx jest <file>`, never Vitest). Inner loop: run the single test file you are editing plus `npm run typecheck` when types change. Run the scoped `verify:*` script once per phase area. Run the full `npm run verify` once, at the final checkpoint.
