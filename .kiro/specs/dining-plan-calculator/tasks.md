## Overview

This plan builds the Dining Plan Calculator specified in `design.md`: shared contracts and two additive menu helpers; migration `0075`; a pure calculation engine; a repo and service that assemble a Trip's party, stay, entries and cached catalog data; Trip routes plus a stateless route; an Admin_Panel section for plan prices, restaurant credit rules and default assumptions; and the mobile Trip screen, its sheets, and the standalone calculator.

Tests ship in the same task as the code they cover. Pure modules get unit tests plus `fast-check` property tests (at least 100 runs, tagged `// Feature: dining-plan-calculator, Property N: <title>`); routes get `server.inject` tests (auth gate, happy path, validation); the repo gets pg-mem tests that run the real SQL and read rows back; the migration gets `migration0075.test.ts`; shared Zod schemas get valid and invalid cases; mobile components get `@testing-library/react-native` interaction tests under `jest-expo` (never Vitest) that assert both the network call and the on-screen change.

Verification tiers (from `.kiro/steering/execution-discipline.md`): while iterating run only the single test file (`npx vitest run <path>` in api and shared, `npx jest <file>` in mobile) and `npm run typecheck` after type changes; run the scoped `npm run verify:shared|api|mobile` at checkpoints; run the full `npm run verify` **once**, at task 13. Paste the literal tail output and exit code, and produce the behavior-to-test map in the final report.

## Notes

- **Verification discipline.** A green `vitest`/`jest` run is not the gate; only `npm run verify` (typecheck and tests across all workspaces) counts. Run it once, at task 13. While iterating, run only the single test file. On Windows, `npm run verify` takes several minutes and exceeds the tool output limit: capture it with `cmd /c "npm run verify > C:\path\out.txt 2>&1"`, read `$LASTEXITCODE`, then `Select-String` the file for `error TS`, `does not meet threshold`, `Test Files`, `Tests` and `Test Suites`. Never overlap two test runs: the heavy catalog property tests fail under load.
- **Shared package.** `apps/api` reads `@dwt/shared` from `packages/shared/dist`. Run `npm run build:shared` after every shared change before API tests or typecheck. A schema that is not in the explicit `index.ts` export lists is `undefined` at runtime in the API.
- **Credits are per person and non-transferable** (Disney's own wording). Do not model a shared pool, even though several third-party guides describe one. Table-service and quick-service credits are never interchangeable; snack credits never become meals.
- **Tax and tip.** Plan prices include tax and out-of-pocket amounts do not; the engine taxes only what is paid out of pocket. Tip is owed on table-service meals in every scenario and is waived only for covered meals at Gratuity_Included locations. This differs from the first proposal (leave tip out); see the design's Decision record.
- **Unverified data.** All child plan prices, all 2027 prices, the calendar-year period boundaries, every `ASSUMPTION` in Configuration & Constants and every derived location rule are unverified and are labelled as estimates in the UI. Mark a rule `verified` only when the seed file's entry cites a Disney channel (the Dining Plans page or a planDisney answer) with its date; never mark anything `verified` from a third-party source or from memory.
- **Do not invent credit costs.** Credit cost 2 (or a period map) may be set in the seed file only for locations named by a source cited in the entry's `sourceNote`, and never in code or a migration; the seed errs on the side of inclusion and every row beyond the Disney-named ones is `unverified`, so the operator deletes wrong rows in the Admin_Panel instead of typing every row.
- **Separate Budget defect found while reviewing (do not fix inside this spec).** In `apps/api/src/services/tripBudget/repo.ts`, `loadBudget` selects `suggestion_key` but never maps it onto the `StoredLine` it builds (only `linkedExpenseId` is mapped), so `GET /trips/:id/budget` reports `suggestionKey: null` for every line. The Dining Plan export does not depend on it (its adapter has its own query). The fix is one line (`suggestionKey: l.suggestion_key` beside `linkedExpenseId`) plus a test in the Budget repo tests; the file currently has uncommitted edits, so make it as its own small change when that work is committed. **Fixed 2026-11-11** after task 13: `loadBudget` now maps the column, and `repo.load.test.ts` ("returns each line's stored suggestionKey") reads a ticket key, a `dining_plan:oop` key and a keyless line back through `loadBudget` on pg-mem; it failed with the mapping removed and passes with it.
- **The Budget export is explicit.** It never runs from a read route or a calculation. It touches only Budget lines whose `suggestion_key` starts with `dining_plan:`, calls the existing Budget repo methods (no Budget code changes), and is retry-safe because the Budget repo calls are separate transactions. Plan costs are tax-inclusive and the Budget stores pre-tax amounts, so the plan lines are converted with the Budget's dining tax rate; tips go in a separate line in category `other` because the Budget taxes every `dining` line.
- **No network, no cron, no worker, no Redis.** The calculator reads cached menus only and never fetches one (Requirement 16.6). Do not wire the retired Disney live modules (`retirement.smoke.test.ts` must stay unmodified and green).
- **Structural guards you will trip if you cut corners.** `roleReader.guard.test.ts` (never import `trips/effectiveRole.ts`; never write a `role FROM trip_memberships` literal), `trip_memberships.guard.test.ts` (this feature adds no `trip_memberships` read; the party comes from the existing ports), `visibility.guard.test.ts` (no new `FROM|JOIN users|profiles`; use `findNonVisibleParties` and the existing ports), the account-deletion registry test (the new Trip tables carry no user FK, so no disposition entry is needed; if the registry test fails, read why before adding one), `themeRetrofit.guard.test.ts` (fix the code, never extend the allowlist).
- **pg-mem versus Postgres.** Never use `ON CONFLICT` against the partial unique index `uq_dpe_planned_item`; check inside the locked transaction instead. `ON CONFLICT (plan_code, valid_from)` and `ON CONFLICT (experience_id)` target a plain unique index and a primary key, which are safe. Run any SQL pg-mem cannot vouch for inside a rolled-back transaction against the local Postgres before relying on it.
- **node-pg returns `SUM()`, `COUNT()` and `BIGINT` as strings.** Convert explicitly; pg-mem returns numbers, so prove the string case with a fake-pool test.
- **Dates.** Use `addDays`/`daysBetween` from `services/ticketPrices/dates.ts` for calendar arithmetic and `wdwMinutesFromMidnight` for time-of-day; never `new Date('YYYY-MM-DD')` in local time. Store no timestamp in this feature except `updated_at`/`created_at`.
- **Edit real source directly.** No codegen or string-replacement scripts, no stray files at the repo root. Wire consumers against the real exported types (open `TripRepo`, `TripExpenseRepo`, `ExperienceDTO`, `MenuDTO` and the budget repo's patterns) and typecheck right after wiring.
- **Mobile tests are Jest (`jest-expo`); api and shared tests are Vitest.** Do not cross them. Every new `.tsx` uses `makeStyles`/`useAppTheme`; one-off colours go in `*.palette.ts`.
- **Known simplifications to keep visible in the UI copy.** Guests under 3 are not priced; fixed-price (buffet, prix fixe) meals are treated as all-in with no separate beverage; alcohol drinkers on all-in bases get no beverage uplift; the pass discount applies party-wide to meals at locations not flagged otherwise; the mug refill works only at resort hotel locations.
- **Out of scope** (do not build without a spec amendment): booking or modifying anything at Disney, fetching live menus or prices at request time, scraping Disney's plan or restaurant-eligibility pages, per-restaurant seasonal pricing, Lightning Lane, Disney Springs-specific rules beyond Location_Rules, comparing dining plans across multiple rooms, sharing a calculation outside Trip members, export, notifications, and a standalone saved calculation.
