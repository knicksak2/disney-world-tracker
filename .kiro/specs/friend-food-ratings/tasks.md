# Implementation Plan

## Overview

Delivers friend-visible dish ratings in two phases, with no migration and no opt-out. Phase 1 adds the shared contracts, the friend-gated per-dish list route, the stats no-note guard, the Friend Food History screen and the Overview Highlights row. Phase 2 adds the batch menu endpoint and inline Social_Proof on menus and the food item picker. Every task ships its own tests; see the Notes and the Task Dependency Graph below for ordering and checkpoints.

## Notes

- **Phases.** Phase 1 (tasks 1–6) delivers the friend-gated list route, the stats no-note guard, the Friend Food History screen and the Highlights row. Phase 2 (tasks 7–8) adds the batch endpoint and inline menu/picker proof and depends on Phase 1 only.
- **Visibility is always on; there is no opt-out, notice or setting.** Friend food-rating visibility for accepted Friends follows the same model as ride/restaurant ratings. Requirements 1, 2, 7, 8, 9 and 10 are withdrawn stubs with no criteria, so no task cites them. A future per-user control would be an additive follow-up (new migration plus a filter in the same queries) and is out of scope.
- **No migration.** This feature creates no table or migration file. Do not add an index without an `EXPLAIN` against a realistic seed; if one is ever wanted it is a new additive `NNNN_name.sql` with a `migrationNNNN.test.ts`.
- **Tests ship in the same task.** No test is deferred or optional. Each task that adds code lists the test layer that covers it: pg-mem repo test for the SQL (2.4, 7.3), source-level no-note SQL guards that forbid `note`, `fil.*`, `food_item_logs.*` and bare `SELECT *`/`RETURNING *` (2.5 for the new repo, 3.5 for the stats repo), `server.inject` route test with auth gate, happy path and a validation-error path (3.2, 7.3), the production-wiring test (3.6, 7.3), shared Zod schema tests with valid and invalid cases (1.2), mobile `@testing-library/react-native` tests that drive each interaction and assert both the request and the on-screen change, including `accessibilityRole`/`accessibilityLabel` on the added controls (4.5, 5.2, 8.4), and fast-check properties (≥100 runs, tagged `// Feature: friend-food-ratings, Property N: ...`) in 2.2, 3.2, 3.4, 4.2, 7.3.
- **Stats path is deliberately unchanged.** `GET /me/stats/summary?for=` keeps returning `foodActivity` to friends (intentional, consistent with always-on visibility). The only stats-related work is the source-level no-note guard (3.5); no stats route, repo or harness is edited, and `stats-experience-redesign` / `friend-stats-viewing` are not edited.
- **pg-mem setup is the precedent, not migration 0004.** The repo test loads `0001` and `0040` only and runs `ALTER TABLE experiences ALTER COLUMN park DROP NOT NULL` (the effect of `0004_disney_sources.sql:75`), recorded as a deviation in task 2.4. Phase 2 also adds `profiles.avatar_preset` by `ALTER TABLE` (task 7.3) because that column comes from `0013`.
- **Highlights also runs the scopes query (accepted).** The Highlights read is the first page of the list route and so executes `listScopes` too; accepted as two indexed request-time queries (design.md A7). No include-scopes parameter is added.
- **Do not reuse owner DTOs.** `FoodItemLogDTO` and `FoodItemLogWithContextDTO` carry `note`. Friend reads use only the new DTOs. Nothing in this feature writes to `food_item_logs`.
- **Do not fold friend data into public routes.** `GET /experiences/:id/food-items` and `GET /locations/:id/food-items` are unauthenticated and stay untouched (task 7.2).
- **Batch reads stay friend-first.** Do not write the batch query item-first.
- **No background work.** No worker, cron, Redis key or push is added anywhere. This structural negative, and the read-only property of the service, are asserted by `friendFoodRatings.noBackgroundWork.test.ts` (task 7.3), not only by review.
- **Theming.** Every new mobile file uses `makeStyles`/`useAppTheme`; a literal colour goes in a co-located `*.palette.ts`. If `themeRetrofit.guard.test.ts` fails, fix the code, never the allowlist.
- **Existing tests that must stay green unchanged:** `MyFoodHistoryScreen.test.tsx`, `foodHistoryFilters.prop.test.ts`, `stats/__tests__/routes.test.ts` (including the friend `foodActivity` case at lines 1034-1070), `stats/__tests__/friendParity.prop.test.ts`, `foodLog/__tests__/routes.test.ts`, and `themeRetrofit.guard.test.ts`. No existing test file is edited except `FriendProfileScreen.modes.test.tsx` (extended in 5.2).
- **useFriendFoodHighlights retryOnMount deviation:** `retryOnMount: false` is configured on `useFriendFoodHighlights` (`apps/mobile/src/hooks/useFriendFoodRatings.ts:103`). While not explicitly specified in design.md (which called out `staleTime: 60_000` and `retry: retryUnlessForbidden`), this mirrors `showcaseQuery` in `FriendProfileScreen` to satisfy Requirement 6.5 ("switching through every mode issues no additional apiRequest calls", asserted by `FriendProfileScreen.refetch.test.tsx`), preventing an errored highlights query from automatically re-requesting upon mode switching and remounting.
- **R6.5 literal search and pg-mem LIKE limitation deviation:** PostgreSQL standard `LIKE` treats backslash `\` as default escape character, matching literal `\%`, `\_`, and `\\`. The pure function `toLikeContainsPattern` implements this and is verified across 100 fast-check runs in `dishAggregate.prop.test.ts:271` (`Property 7: LIKE escaping matches %, _, \\ literally`). In `pg-mem`, `buildLikeMatcher` (`pg-mem/index.js:390`) does not support the `ESCAPE` clause and treats all backslashes as literal regex characters rather than escape characters, translating `\%` to `.*\\.*.*`. Substring search through `listDishes` with `toLikeContainsPattern` is verified in `friendFoodRatings.repo.test.ts`, while literal `%`, `_`, and `\` escaping coverage resides in the pure-function property test.
- **Pin gate not applicable.** No catalogue or artwork file changes, so `.kiro/specs/pin-collection/verify/run-all.js` is not run.
- **Cross-spec dependencies and build order.** Requires `food-item-logging`, `friend-stats-viewing`, `stats-experience-redesign` (food stats, read as-is), `restaurant-menu-display` (Phase 2) and `dark-mode`. No other spec is amended. See requirements.md "Relationship to Existing Friend Visibility".

### Open Questions / Assumptions

No open questions remain. Each default below is recorded in design.md (Overview, Open Questions / Assumptions and Configuration & Constants).

- **Friend stats are unchanged** (design.md A1): friends keep seeing `foodActivity`; no projection or narrowing.
- **Aggregation:** friends see the average of rated logs plus counts, not the latest rating.
- **Unrated-only dishes** appear in the full list as "Not rated" and are excluded from Highlights and inline proof.
- **Highlights threshold is 1 rated log** (`FRIEND_FOOD_HIGHLIGHT_MIN_RATED_LOGS`), below the Stats minimum of 2, because a friend wants the single-visit signal and the full list already shows every dish.
- **Batch endpoint** resolves the whole scope server-side (no dish-id list in the request); a missing scope returns `{ items: [] }`; the row cap is response-side.
- **Deactivated experiences and off-menu dishes** are included, matching My Food History.
- **pg-mem function support** (`to_char`, `LIKE ... ESCAPE`, `AVG`, casts) is verified when writing task 2.4; any unsupported construct is registered the way existing prop tests register missing functions, and a behaviour-equivalent fallback is used only where pg-mem cannot parse the real SQL, with the deviation recorded in the task.
